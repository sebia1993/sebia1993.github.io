DNS-01 · A Query / Response + 실제 IP 통신 PASS

PC1은 app.lab.test A/IN Query를 R2에 보냈고 Client-side DNS ID 21456과 같은 ID의 Response에서 A=203.0.113.10, TTL 10을 받았습니다. 이후 Name Ping의 ICMP Request/Reply도 CP1/CP3/CP4에서 대응됐고 3/3 성공했습니다.

DNS-02 · Recursive / Upstream Resolution PASS

PC1 Query는 RD=1이었고 R2 Cache Miss 시 R2가 R3에 별도 Upstream Query를 보냈습니다. Client Leg DNS ID는 21456, Upstream Leg ID는 31909였으며 R3는 AA=1, A=203.0.113.10을 반환했습니다.

구현 경계: Resolver가 Upstream DNS ID를 재작성했으므로 두 Leg를 ID equality만으로 연결하면 안 됩니다. QNAME/QTYPE, Endpoint, 시점과 각 Leg ID를 함께 봅니다.

DNS-03 · Cache Miss → Cache Hit PASS

첫 PC1 Query는 R3까지 가서 TTL 10 Answer를 만들었습니다. 약 3.6초 뒤 PC2가 같은 이름을 조회하자 R2는 TTL 6 Cached Answer를 반환했고 두 번째 Query에 대응하는 새 Upstream Query는 CP4에서 0이었습니다.

First miss: AA1 / TTL10 · Second hit: AA0 / TTL6 · upstreamSecondQueries=0

DNS-04 · DNS Service Down / Recovery PASS after revalidation

최종 Run: R2 DNS Service를 중지해도 PC1→203.0.113.10 IP Ping은 3/3 유지됐습니다. down.lab.test Query는 R2까지 도착했지만 DNS Response는 0, Upstream Query도 0이었고 Client는 Cannot resolve 후에도 같은 Process로 CLI를 계속 사용할 수 있었습니다. Service 복구 후 Client 재시작 없이 Name Ping 3/3이 복구됐습니다.

Actual 차이: 이번 IOS는 DNS Service Down 시 ICMP Type3 Code3을 반환했습니다. 이를 모든 DNS 장애의 일반적인 “silent timeout”으로 가르치지 않습니다.

DNS-05 · Wrong Client DNS / Recovery PASS after revalidation

PC1 DNS를 존재하지 않는 192.0.2.254로 바꾸자 Direct IP Ping은 계속 3/3이었지만 .254 ARP Request 3개에 Reply는 0, 실제 R2 Resolver Query도 0이었습니다. DNS 주소만 198.51.100.2로 되돌린 뒤 Client 재시작 없이 wrong.lab.test Answer와 Name Ping 3/3이 복구됐습니다.

DNS-06 · NXDOMAIN vs Timeout PASS

R3에서 recover.lab.test Record를 제거하고 R2 Cache를 비운 뒤 Query하자 R3는 AA=1, RCODE=3, A Answer 0개의 NXDOMAIN Response를 실제로 반환했고 R2도 Client에 RCODE=3을 전달했습니다. Record 복구 후 PC2는 RCODE=0, A=203.0.113.10을 받아 Name Ping 3/3에 성공했습니다.

핵심: NXDOMAIN은 DNS Error Response가 존재하는 상태이며 DNS Service Down의 “DNS Response 없음”과 다릅니다.

VALIDATION RESOLUTION

첫 Run의 DNS-04/05 INCONCLUSIVE는 보존했습니다.

첫 Run의 VPCS 1.0(0.8c)에서는 DNS 실패 경로 중 Worker segfault가 커널 로그에 남아 Service-only / DNS-setting-only Recovery를 같은 실행 Client에서 증명할 수 없었습니다. 공식 VPCS DNS 오류 수정이 포함된 upstream 0.8.4 고정 소스를 이 DNS Lab의 PC1/PC2에만 적용해 재검증했습니다.

최종 정식 재검증 구간의 Client 재시작은 0회였고 PID/start ticks/executable hash가 유지됐습니다. 구형 stripped PNET 바이너리의 정확한 fault instruction을 소스 줄에 독립 매핑한 것은 아니므로, “공식 결함과 일치하는 증상 + 수정본 재현 결과” 범위로만 원인을 설명합니다.

검증 한계

이번 Lab의 Actual 범위를 넘기지 않습니다.

R2는 configured upstream R3를 사용하는 Cisco Caching Resolver입니다. Root/TLD 전체 Iterative Resolution을 검증하지 않았습니다. Authoritative A TTL은 이번 Run에서 10초, Cache Hit는 6초였으며 보편 TTL이 아닙니다.

Cache-miss forwarded Answer에서 AA=1, Cache-hit Answer에서 AA=0이 관찰됐지만 이를 모든 Resolver 구현의 고정 규칙으로 일반화하지 않습니다. VPCS는 A 실패 뒤 AAAA Query도 보냈으며 NXDOMAIN A Result와 분리해 원본 Evidence에 보존했습니다.
