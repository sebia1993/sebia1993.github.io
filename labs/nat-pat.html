NAT / PAT

목표는 하나입니다. Inside에서 Outside로 나갈 때 어떤 주소/Port가 바뀌고, Translation Table이 Return Traffic을 어느 Inside Host로 되돌리는지 설명할 수 있으면 됩니다.

NAT는 “주소를 바꾸는 기능”만이 아닙니다.Outside에서 돌아오는 Packet을 원래 Inside Flow와 다시 연결하는 Translation State까지 함께 봐야 합니다.
1 · 개념서2 · Interactive Lab
Inside Local → Translation Table → Inside Global → Outside → Return Translation → Inside Local

PAT는 여러 Inside Flow가 하나의 Global IP를 공유할 수 있도록 Flow 구분값을 함께 기록합니다.

00 · 30초 핵심

NAT는 Packet의 “Inside에서 보이는 값”과 “Outside에서 보이는 값”을 연결합니다.

1

Role

Packet이 NAT inside에서 outside로 지나가는지 확인합니다.

2

Match

이 Packet이 NAT 대상으로 선택되는지 확인합니다.

3

Translate

Inside Local을 Inside Global로 바꾸고 Translation을 기록합니다.

4

Return

응답은 Translation Table을 이용해 원래 Inside endpoint로 돌아갑니다.

01 · TOPOLOGY

R2만 NAT Edge이고 R1·R4는 Inside, R3는 Outside입니다.

R110.0.11.2
Inside A
R410.0.14.2
Inside B
R2E0/0·E0/1 inside
E0/2 outside
R3198.51.100.2
Outside
검증 설계: Routing은 고정하고 NAT 변수만 바꿨습니다. 그래서 실패 Scenario에서도 Packet이 CP23까지 나가는지, 주소가 변환됐는지를 분리해서 판단할 수 있습니다.
02 · BASIC NAT

R1의 Inside Local 주소가 Outside에서는 198.51.100.5로 보였습니다.

INSIDE · CP11

Source = 10.0.11.2

R1이 R3로 ICMP를 보낼 때 Inside 구간에서는 원래 주소가 그대로 보입니다.

10.0.11.2 → 198.51.100.2
OUTSIDE · CP23

Source = 198.51.100.5

같은 Packet이 NAT Edge를 지나면 Source만 Inside Global 주소로 바뀌고 Destination은 유지됐습니다.

198.51.100.5 → 198.51.100.2
Inside Local · 10.0.11.2→ NAT →Inside Global · 198.51.100.5
Actual: R1 Ping 3/3 성공, CP11/CP23 Packet과 Translation Table mapping이 일치했습니다.
03 · PAT OVERLOAD

R1과 R4가 하나의 Global IP를 동시에 공유했습니다.

10.0.11.2:25473→198.51.100.5:25473 → R3:23
10.0.14.2:46258→198.51.100.5:46258 → R3:23
중요: 이번 Run에서는 두 TCP source port가 NAT 전후에 그대로 유지됐습니다. 따라서 PAT를 “항상 Port 번호를 바꾼다”고 외우면 안 됩니다. 핵심은 같은 Global IP에서 각 Flow를 구분할 수 있는 Translation mapping입니다.
RETURN · R1 SESSION

Global :25473 → Local :25473

R3의 응답은 Translation Table을 보고 CP11의 R1 Flow로만 되돌아왔습니다.

RETURN · R4 SESSION

Global :46258 → Local :46258

같은 Global IP를 쓰지만 R4 Flow는 CP14로 정확히 분리됐고 다른 Inside Link의 대응 응답은 0개였습니다.

04 · STATIC PAT

Outside의 :2323을 Inside R1의 :23 서비스로 연결했습니다.

R3 → 198.51.100.5:2323→ R2 NAT →10.0.11.2:23 · R1
OUTSIDE VIEW

Destination = .5:2323

R3에서 보낸 SYN은 CP23에서 Inside Global endpoint를 향했습니다.

INSIDE VIEW

Destination = 10.0.11.2:23

R2를 지난 뒤 CP11에서는 R1의 실제 서비스 endpoint로 변환됐고 3-way handshake와 prompt 도달이 확인됐습니다.

05 · FAILURE / RECOVERY

NAT 실패가 반드시 R2에서 Packet Drop을 의미하는 것은 아닙니다.

NAT-05 · SELECTION MISMATCH

R4는 “차단”이 아니라 “미변환”

R1만 NAT 대상으로 선택하자 R4는 Translation entry가 생성되지 않았습니다. 하지만 R4 Request는 CP23까지 10.0.14.2 그대로 전달됐습니다.

R4 CP14 → R2 → CP23 · source 10.0.14.2 유지 · R3 return route 없음 → 0/3
NAT-06 · INSIDE ROLE MISSING

Routing은 되지만 Translation이 없음

R1 쪽 NAT inside role만 제거하자 R1 Packet은 CP23까지 나갔지만 Source가 10.0.11.2 그대로였습니다. 같은 시점 R4는 정상 변환돼 3/3이었습니다.

R1 0/3 · R4 control 3/3 · role 복구 후 R1/R4 모두 3/3
핵심: NAT Selection list는 보안 ACL처럼 “Permit 아니면 Drop”으로 해석하면 안 됩니다. 이번 검증에서 R4 Packet은 실제로 Outside까지 Forward됐지만 Translation State가 없어 Return Path가 성립하지 않았습니다.
06 · REVIEW

여기까지만 연결해서 설명할 수 있으면 1단계 완료입니다.

⭐ 꼭 기억하세요

  • Inside Local은 내부에서 보이는 주소, Inside Global은 외부에서 보이는 주소입니다.
  • Basic NAT는 주소 mapping, PAT는 여러 Flow가 같은 Global IP를 공유할 수 있게 mapping을 확장합니다.
  • Return Traffic은 Translation Table을 보고 정확한 Inside Flow로 되돌아옵니다.
  • Static PAT는 Global IP:Port를 Inside Service IP:Port에 고정 연결할 수 있습니다.
  • NAT 실패는 “Drop”과 “미변환 후 Return 실패”를 구분해야 합니다.
내 말로 설명하기

“R4 Packet이 CP23까지 나갔는데 왜 Ping은 실패할까?”
