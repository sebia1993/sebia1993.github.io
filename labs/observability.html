01 · 질문과 그림으로 시작

통신이 끊겼다는 결과만으로 원인과 복구를 설명할 수 있을까요?

30초 핵심 · 서로 다른 관측 자료는 서로 다른 질문에 답합니다. 한 자료로 원인을 확정하기보다 같은 장비와 인터페이스의 변화인지 연결하고 복구 결과도 확인합니다.

02 · 방금 본 그림에 이름 붙이기

이름보다 역할을 먼저 기억하세요.

Packet Capture / Syslog
링크에서 보인 패킷의 기록과, 장비가 남기거나 보내는 사건 로그입니다.
SNMP GET / Trap
GET은 현재 상태를 묻는 요청, Trap은 장비가 보내는 비동기 알림입니다.
Correlation · 연관 확인
시간·장비·인터페이스를 맞춰 서로 다른 자료가 같은 사건을 가리키는지 확인하는 일입니다.

03 · 동작 순서

핵심 흐름을 연결해 봅니다.

  1. 정상 통신과 상태를 먼저 기록합니다.
  2. 문제 구간의 패킷·로그·현재 상태를 확인합니다.
  3. 자료들이 같은 장비와 상태 전환을 가리키는지 연결합니다.
  4. 복구 뒤 실제 통신과 상태가 다시 정상인지 함께 봅니다.

04 · 헷갈리는 지점

헷갈리는 의미를 구분해서 읽으세요.

구분뜻
설정 상태 · Admin관리자가 인터페이스를 어떻게 설정했는지입니다.
동작 상태 · Oper인터페이스가 실제로 동작하는 상태입니다. 설정 의도와 구분해서 확인합니다.

05 · 복습

꼭 기억할 세 가지

  • Ping 실패 하나로 원인을 확정하지 않습니다.
  • 상태 조회와 변화 알림은 다른 자료입니다.
  • 자료의 도착 시각이 정확히 같지 않아도 같은 사건일 수 있습니다.

1단계 · CONCEPT GUIDE

Packet / Log / SNMP 관측

Ping이 끊겼다는 사실만 알면 장애 원인까지 알 수 있을까요? 아닙니다. “통신이 안 됐다”와 “장비에서 어떤 일이 일어났는가”는 다른 질문입니다. 여러 종류의 증거를 같은 사건으로 연결해야 원인과 복구를 더 정확하게 설명할 수 있습니다.

사건 하나 → Packet · Log · 상태 조회 · 알림 → 시간과 대상 장비로 묶기 → 복구까지 확인

한 증거가 모든 것을 말해 주지는 않습니다. 서로 다른 증거가 같은 인터페이스의 같은 상태 변화를 가리키는지 확인하는 것이 핵심입니다.

00 · 첫 질문

Ping 0/3이면 무엇까지 말할 수 있을까?

관측된 사실R1에서 R2로 보낸 Ping 응답이 0/3
?
아직 모르는 것케이블? 인터페이스? 정책? 장비 상태? 어느 시점에 바뀌었나?
30초 핵심: Packet Capture는 링크에서 무엇이 실제로 보였는지, Log는 장비가 어떤 사건을 기록했는지, SNMP는 장비 상태를 조회하거나 상태 변화 알림을 받는 데 사용합니다. 세 가지를 한 사건의 시간 흐름으로 연결합니다.

02 · EVIDENCE TYPES

서로 다른 증거는 서로 다른 질문에 답합니다.

PACKET CAPTURE

“링크에서 무엇이 보였나?”

실제로 지나간 Packet과 그 시각을 확인합니다. 장애 때 Packet이 안 보였다는 주장에는 정상 전후 대조도 필요합니다.

Wire Evidence
SYSLOG

“장비가 어떤 사건을 기록했나?”

장비가 인터페이스 down/up 같은 사건을 문장 형태로 기록하거나 외부로 전송합니다.

Event Record
SNMP GET

“지금 상태가 어떤가?”

관리 단말이 장비에 질문을 보내고, 장비가 관리용으로 제공하는 상태 항목(MIB Object)의 현재 값을 응답으로 읽습니다. 이번 검증에서는 Admin/Oper 상태를 확인했습니다.

Request → Response
SNMP TRAP

“상태가 바뀌었다고 알려왔나?”

장비가 Manager의 질문을 기다리지 않고 상태 변화 Notification을 보냅니다.

Asynchronous Notification

Trap이 항상 가장 먼저 오는 것은 아닙니다.

이번 Run에서는 linkDown Trap이 장애 상태 SNMP GET 응답보다 늦게 도착했습니다. Syslog·Trap·Polling은 서로 비동기적일 수 있으므로 “정확히 같은 시각”보다 같은 인터페이스와 같은 상태 전환을 가리키는지 확인합니다.

05 · POLLING VS NOTIFICATION

SNMP에서도 “묻기”와 “알려주기”는 다릅니다.

구분누가 시작?무엇을 확인?이번 관측
SNMP GETNMS1 Manager현재 MIB 상태1/1 → 2/2 → 1/1
SNMP TrapR1 Agent상태 변화 알림linkDown / linkUp
ADMIN vs OPER

설정 상태와 실제 동작 상태를 구분합니다.

ifAdminStatus는 관리자가 의도한 상태, ifOperStatus는 실제 동작 상태입니다. 이번 shutdown에서는 둘 모두 1→2→1로 바뀌었습니다.

TRAP LIMIT

Trap에 없는 값을 만들어내지 않습니다.

이번 linkDown/linkUp Trap에는 ifIndex와 인터페이스 설명은 있었지만 ifAdminStatus/ifOperStatus varbind는 없었습니다. 그 상태값은 GET 응답으로 확인했습니다.

06 · RECOVERY GATE

“no shutdown 했다”와 “복구됐다”는 같은 말이 아닙니다.

복구 명령

설정을 원래대로 돌리는 행동입니다. 이것만으로 서비스가 정상이라고 확정하지 않습니다.

복구 Evidence

Interface up/up, Ping 3/3, SNMP 1/1, Syslog up, linkUp Trap, 관리 경로 정상까지 서로 모순이 없는지 확인합니다.

추가 구분: 이번 검증에서 SNMP 관리 기능이 시작된 뒤의 경과 시간인 sysUpTime은 장애 전후 계속 증가했습니다. 따라서 Data Interface가 내려갔다는 사건을 장비 전체 재부팅으로 오해하지 않습니다.
07 · REVIEW

이 다섯 문장을 설명할 수 있으면 1단계 완료입니다.

⭐ 꼭 기억하세요

  • Ping 실패만으로 장애 원인을 확정하지 않습니다.
  • Packet, Syslog, SNMP는 서로 다른 종류의 증거입니다.
  • SNMP GET은 현재 상태를 묻고, Trap은 변화 사실을 비동기적으로 알립니다.
  • 여러 Source의 timestamp가 정확히 같을 필요는 없습니다.
  • 복구는 여러 Evidence가 다시 정상 상태와 일치할 때 확인합니다.
