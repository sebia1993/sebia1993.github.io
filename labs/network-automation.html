01 · 질문과 그림으로 시작

장비 여러 대를 매번 같은 기준으로 빠짐없이 확인하려면 어떻게 해야 할까요?

30초 핵심 · 자동화는 명령을 빨리 입력하는 것보다 같은 대상과 기준으로 읽고 비교하고 기록하는 과정입니다. 읽은 상태가 다르다는 것과 아예 읽지 못했다는 것을 구분합니다.

02 · 방금 본 그림에 이름 붙이기

이름보다 역할을 먼저 기억하세요.

Inventory / Intent
확인할 장비 목록과 미리 정한 정상 기준입니다.
Raw / Normalize
장비가 반환한 원문과 이를 같은 형태의 필드로 정리하는 과정입니다.
Report / Re-run
판정 결과 기록과 같은 절차의 재실행입니다. 실제값을 확보하지 못하면 상태 불일치로 추측하지 않습니다.

03 · 동작 순서

핵심 흐름을 연결해 봅니다.

  1. 대상 목록과 정상 기준을 읽습니다.
  2. 장비에서 상태를 수집하고 원문을 남깁니다.
  3. 비교할 필드를 같은 형태로 정리합니다.
  4. 정상 기준과 비교해 결과를 기록합니다.
  5. 수정·복구 뒤 같은 절차를 다시 실행해 핵심 판정을 확인합니다.

1단계 · CONCEPT GUIDE

Network Automation

Router 3대의 같은 상태를 매번 사람이 한 대씩 확인해야 할까요? 자동화는 단순히 명령을 빨리 입력하는 것이 아니라, 같은 기준으로 여러 장비를 읽고 비교하고 기록하는 과정입니다.

확인할 장비와 정상 기준 → 자동 수집 → 같은 형태로 정리 → 비교 → 결과 기록 → 다시 실행

이번 학습에서는 설정을 자동 변경하지 않습니다. 먼저 읽기 전용 상태 점검을 정확하고 반복 가능하게 만드는 데 집중합니다.

03 · MENTAL MODEL

자동화는 여섯 단계로 보면 됩니다.

1

대상 읽기

Inventory에서 R1/R2/R3를 가져옵니다.

2

수집

SSH로 각 장비에 같은 상태를 요청합니다.

3

Raw 보존

장비가 반환한 원문을 남깁니다.

4

정규화

비교할 값을 같은 구조로 바꿉니다.

5

Intent 비교

Actual과 정상 기준이 같은지 판정합니다.

6

Report

장비별 결과와 전체 요약을 이름-값 구조의 텍스트 형식인 JSON으로 남깁니다.

04 · RESULT MODEL

PASS, MISMATCH, ERROR는 서로 다릅니다.

PASS

읽었고, 정상 기준과 같음

SSH 수집 성공 → 상태 파싱 성공 → Actual이 Intent와 일치합니다.

MISMATCH

읽었지만, 상태가 다름

장비에는 정상 접속했고 실제 상태도 읽었지만, Actual이 Intent와 다릅니다.

ERROR

비교 전에 수집 자체가 실패

연결 또는 수집 실패 때문에 상태를 읽지 못했습니다. Actual을 임의로 만들지 않습니다.

“실패”라는 한 단어로 합치지 마세요.

R2 MISMATCH는 R2에 정상 접속한 뒤 Loopback0이 기대와 다르다는 뜻이고, R3 ERROR는 테스트용 잘못된 SSH 포트 때문에 상태 비교 자체를 하지 못했다는 뜻입니다. R3 장비 장애를 의미하지 않습니다.

05 · ACTUAL RUN

실제 검증에서는 결과가 이렇게 바뀌었습니다.

실행PASSMISMATCHERROR전체
Baseline300PASS
R2 상태 불일치210NON_PASS
R2 복구300PASS
R3 수집 오류201NON_PASS
최종 복구300PASS
MISMATCH CASE

R2 Loopback0만 수동 shutdown

SSH 수집은 성공했습니다. 하지만 Actual은 administratively down/down이어서 R2만 MISMATCH가 됐고 R1/R3는 PASS를 유지했습니다.

ERROR CASE

복사 Inventory에서 R3 포트만 변경

R3의 실제 장비 상태는 바꾸지 않고 접속 포트만 사용하지 않는 값으로 바꿨습니다. R3는 ERROR/NOT_EVALUATED였고 R1/R2 결과는 보존됐습니다.

06 · REPEATABILITY

자동화는 다시 실행했을 때도 같은 기준이어야 합니다.

Baseline

R1/R2/R3 모두 SUCCESS/PASS. Script와 원본 Inventory의 SHA-256을 고정한 뒤 시작했습니다.

Final

R2 상태와 원본 Inventory를 모두 복구한 뒤 다시 3 PASS. 장비별 핵심 상태 묶음(Tuple)과 Script/Inventory의 파일 지문(hash)이 Baseline과 같았습니다.

왜 중요한가? run_id나 생성 시각은 실행마다 바뀔 수 있습니다. Repeatability는 모든 글자가 똑같다는 뜻이 아니라, 같은 입력·같은 장비 상태에서 핵심 판정이 다시 같아야 한다는 뜻입니다.
07 · 구현과 원리 구분

이번에는 SSH/CLI로 검증했지만 자동화의 본체는 더 넓습니다.

공통 원리

Inventory → Collect → Normalize → Compare → Report → Re-run 구조는 Transport가 바뀌어도 재사용할 수 있는 자동화 Mental Model입니다.

이번 구현

Cisco IOL, Python 3.11, SSH/CLI 작업을 돕는 Python Library인 Netmiko 4.8과 그 하위 SSH Library인 Paramiko 4.0을 사용했습니다. RESTCONF·NETCONF·gNMI·설정 Push는 이번 주제에서 검증하지 않았습니다.

SSH PCAP에서 명령 내용이 보였다고 주장하지 않습니다.

SSH Payload는 암호화됩니다. PCAP은 NMS1과 각 Router 사이의 SSH Transport Session과 연결 실패를 증명하고, 실제 명령/결과 내용은 NMS1 Raw Artifact와 Router Console로 대조했습니다.

08 · REVIEW

이 다섯 문장을 설명할 수 있으면 1단계 완료입니다.

⭐ 꼭 기억하세요

  • 자동화는 같은 기준으로 여러 장비를 반복 확인하는 과정입니다.
  • Inventory는 대상 목록, Intent는 정상 기준입니다.
  • Raw Output과 정규화된 데이터는 구분합니다.
  • MISMATCH와 ERROR는 원인이 다른 결과입니다.
  • 복구 후 같은 자동화를 재실행해 핵심 상태가 Baseline과 같은지 확인합니다.
내 말로 설명하기

“R2는 MISMATCH인데 R3는 ERROR라면, 두 장비에서 실제로 무엇이 다르게 일어난 걸까?”

수집 성공 여부 → Actual 존재 여부 → Intent 비교 가능 여부 → 최종 판정 순서로 설명해 보세요.
