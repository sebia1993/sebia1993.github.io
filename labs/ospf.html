OSPF

이웃과 연결 정보를 맞추고 누적 Cost로 경로를 계산하는 흐름을 설명합니다.

앞선 학습 · Routing Table / Static / Default Route까지의 개념을 연결합니다.

01 · 질문과 그림으로 시작

라우터들이 지도를 공유하면 길이 끊겼을 때 어떻게 새 길을 찾을까요?

30초 핵심 · OSPF는 라우터들이 연결 상태 정보를 주고받는 라우팅 프로토콜입니다. 같은 영역의 정보를 바탕으로 비용 합이 낮은 경로를 계산하고, 연결이 바뀌면 다시 계산합니다.

02 · 방금 본 그림에 이름 붙이기

이름보다 역할을 먼저 기억하세요.

Neighbor / Area
OSPF 정보를 교환하는 이웃과 정보를 묶어 관리하는 영역입니다. 이 예제는 Area 0입니다.
LSA / LSDB
연결 상태를 알리는 정보가 LSA이고, 이를 모은 지도가 LSDB입니다.
SPF / Cost
지도에서 비용 합이 낮은 길을 계산하는 방식이 SPF입니다. 링크별 평가값 Cost를 사용합니다.

03 · 동작 순서

핵심 흐름을 연결해 봅니다.

  1. Hello 메시지로 이웃을 발견하고 정보 교환 관계를 만듭니다.
  2. 같은 영역의 연결 상태 정보를 맞춥니다.
  3. 누적 Cost로 목적지까지의 경로를 계산합니다.
  4. 계산한 경로를 반영하며 연결이 바뀌면 다시 계산합니다.

04 · 헷갈리는 지점

헷갈리는 의미를 구분해서 읽으세요.

구분뜻
이웃 상태 FULL연결 상태 정보의 동기화가 완료된 관계입니다.
실제 데이터 경로로 선택목적지에 대한 경로 계산 결과입니다. FULL인 모든 이웃을 항상 데이터 경로로 쓰지는 않습니다.

05 · 복습

꼭 기억할 세 가지

  • 이웃 → 지도 → 계산 → 전달 경로를 연결해서 봅니다.
  • 직접 연결이 항상 더 낮은 Cost는 아닙니다.
  • 장애 후에는 남은 지도로 경로를 다시 계산합니다.

1단계 · CONCEPT GUIDE

OSPF

목표는 하나입니다. OSPF가 이웃과 Link-State 정보를 맞춘 뒤 Cost가 가장 낮은 경로를 선택하고, 장애가 생기면 대체 경로로 다시 계산하는 흐름을 설명할 수 있으면 됩니다.

OSPF는 “Neighbor가 FULL인가?”에서 끝나지 않습니다.Neighbor → LSDB → SPF/Cost → Routing Table → 실제 Packet Path를 연결해서 봅니다.
1 · 개념서2 · Interactive Lab
Hello → Neighbor → LSA / LSDB → SPF → Lowest Cost Path → Routing Table

장애가 생기면 Adjacency 또는 Topology가 바뀌고, LSDB·SPF·Next Hop이 다시 계산됩니다.

00 · 30초 핵심

OSPF는 같은 Area의 지도를 맞추고 가장 낮은 Cost 길을 고릅니다.

1

Hello

직접 연결된 OSPF Router가 서로를 발견합니다.

2

Neighbor

조건이 맞으면 Adjacency가 진행되어 FULL에 도달합니다.

3

LSA / LSDB

같은 Area의 Link-State 정보를 공유해 같은 지도를 만듭니다.

4

SPF / Cost

누적 Cost가 가장 낮은 경로를 계산합니다.

5

Route

계산 결과의 Next Hop이 Routing Table과 실제 경로에 반영됩니다.

02 · COST / SPF

R1은 직접 R3보다 R2를 거치는 길을 선택했습니다.

SELECTED PATH

R1 → R2 → R3 = Cost 21

R1-R2 10 + R2-R3 10 + R3 Loopback 1 = 21. R1의 3.3.3.3/32 Next Hop은 10.0.12.2였습니다.

R1 ━▶ R2 ━▶ R3 · CP12 → CP23
BACKUP PATH

R1 → R3 = Cost 51

직접 링크 50 + R3 Loopback 1 = 51. Neighbor는 FULL이지만 Cost가 더 높아서 정상 상태의 데이터 경로로 선택되지 않았습니다.

R1 ┄▶ R3 · CP13 · 정상 선택 아님
중요: “Neighbor가 FULL이다”와 “그 Neighbor를 현재 트래픽 경로로 사용한다”는 같은 뜻이 아닙니다. 이번 Baseline에서는 CP13 Neighbor도 FULL이지만 실제 3회 Ping 흐름은 CP12/CP23에만 있었습니다.
03 · FAILURE / RECOVERY

장애 원인에 따라 Adjacency가 깨지는 지점은 다르지만 대체 경로는 살아 있었습니다.

AREA MISMATCH

Area 1 ↔ Area 0

R1-R2 링크에서 R1만 Area 1로 바꾸자 안정화 후 양쪽 Neighbor Table에서 상대가 사라졌습니다. CP12 Hello에는 Area 1과 Area 0이 실제로 함께 관측됐습니다.

CP12 adjacency ✕ · CP13/CP23 FULL · 트래픽은 CP13 3/3
MTU MISMATCH

IP MTU 1400 ↔ 1500

R1-R2 재협상에서 양쪽 Neighbor가 실제로 EXSTART에 머물렀고, DBD Interface MTU 1400/1500과 반복 Sequence를 PCAP으로 확인했습니다.

DBD negotiation STOP · CP13 3/3 · 1500/1500 복구 후 FULL
LINK FAILURE

선호 R1-R2 Link Down

R1-R2를 내리자 R1 Router-LSA가 바뀌고 3.3.3.3/32 Route는 Next Hop 10.0.13.2, Cost 51로 변경됐습니다.

Cost 21 path ✕ → Cost 51 CP13 ✓ → 복구 후 Cost 21
주의: Area mismatch나 Link Down 직후 Neighbor 상태는 양쪽에서 동시에 변하지 않을 수 있습니다. 또한 EXSTART는 여러 원인이 있을 수 있습니다. 이번 검증에서는 MTU 설정과 DBD 필드를 함께 확인했기 때문에 MTU 원인으로 판정했습니다.
04 · CONVERGENCE

장애가 끝나면 원래 더 낮은 Cost 경로로 다시 돌아왔습니다.

FAILURE

Next Hop 10.0.13.2 · Cost 51

선호 Link가 사라진 동안 R1은 남아 있는 직접 R3 경로로 재계산했습니다. CP13에서 Ping 3/3이 확인됐습니다.

RECOVERY

Next Hop 10.0.12.2 · Cost 21

R1-R2 Link와 FULL adjacency가 복구된 뒤 Routing Table과 Packet Path는 다시 R1→R2→R3로 돌아왔습니다.

수렴 시간: 이번 학습에서는 “경로가 다시 계산되어 바뀐다”를 배웁니다. 정확한 ms 단위 수렴 시간은 이번 검증의 보편 Claim으로 사용하지 않습니다.
05 · REVIEW

여기까지만 연결해서 설명할 수 있으면 1단계 완료입니다.

⭐ 꼭 기억하세요

  • Hello → Neighbor → LSDB → SPF → Route 순서로 연결해서 봅니다.
  • 같은 Area의 Router는 Link-State 정보를 공유해 LSDB를 맞춥니다.
  • OSPF는 누적 Cost가 더 낮은 경로를 선택합니다.
  • FULL Neighbor가 있어도 그 Link가 현재 데이터 경로로 선택됐다는 뜻은 아닙니다.
  • Area/MTU/Link 장애는 각각 Adjacency와 경로에 다른 방식으로 영향을 주며, 복구 후 다시 수렴합니다.
