Broadcast의 목적지 MAC은 ff:ff:ff:ff:ff:ff입니다. 여기서 PC3에 보인 Unknown Unicast는 PC2의 실제 MAC을 목적지로 사용합니다. “Unknown”은 PC1이 아니라 Switch의 FDB 관점입니다.

PC3 링크에 보였다는 것과 PC3가 응답했다는 것은 다릅니다.

04번의 GNS3 링크 캡처에는 목적지 MAC이 PC2인 요청 프레임 1개가 있습니다. 이는 SW1이 PC3 쪽 링크에도 복제·전달했다는 근거입니다. 목적지가 PC3로 바뀌거나 Broadcast로 변환된 것은 아닙니다.

일반적인 호스트 수신 필터링에서는 자기 MAC이 아닌 Unicast를 자기 IP 통신으로 처리하지 않습니다. 다만 이 실험은 PC3 내부의 NIC 필터나 IP 스택을 추적하지 않았으므로, 캡처만으로 PC3 내부의 처리·폐기 위치를 판정하지 않습니다. PC3 링크의 해당 캡처에는 요청 1개만 있고 응답 프레임은 없습니다.

04 · TWO TABLES, DIFFERENT ROLES

ARP가 남아 있어도 Switch는 모를 수 있습니다.

ARP · IP → MAC

누구에게 보낼 프레임인가?

PC1은 .20이 00:50:79:66:68:01임을 알고 있었습니다. 캐시가 남아 새 ARP 없이 바로 Unicast를 만들었습니다.

FDB · MAC → PORT

어느 포트로 내보낼 것인가?

SW1에서 PC2 포트의 학습 항목만 지웠습니다. 목적지 위치가 없어 요청이 PC2뿐 아니라 PC3 포트에도 전달됐습니다.

Source MAC Learning

응답이 돌아오면 다시 배웁니다.

PC2의 응답을 port 2에서 받고 PC2 MAC을 재학습했습니다. 다음 요청 3개는 PC3로 Flooding되지 않았습니다.

이번 FDB 삭제는 새 Bridge의 eth1을 잠깐 분리·재등록한 방식입니다. 실제 Aging 관찰은 06번에서 별도로 수행했습니다. 물리 스위치나 모든 VLAN 정책의 동작을 검증한 것은 아닙니다.

Switch는 어느 MAC으로 학습하는가?

Source MAC입니다. PC2 응답을 막았을 때 FDB에 PC1만 생겼고, PC2의 ARP Reply를 받은 뒤 PC2가 추가됐습니다.

Destination MAC을 모르면 어디로 보내는가?

실험 근거와 대조하기

이번 동일 Bridge에서 수신 포트를 제외한 나머지 포트로 Flooding했습니다. PC2로 가는 요청이 PC3에서도 같은 바이트로 잡혔습니다.

Known Unicast는 어떻게 전달되는가?

실험 근거와 대조하기

FDB에 기록된 목적지 포트로 보냅니다. PC1→PC2 요청 3개가 PC2 링크에만 나가고 PC3에는 없었습니다.

Broadcast와 Unknown Unicast의 차이는?

실험 근거와 대조하기

둘 다 Flooding됐지만 Broadcast는 ff:ff:ff:ff:ff:ff, Unknown Unicast는 PC2의 실제 MAC 00:50:79:66:68:01을 목적지로 사용했습니다.

MAC Entry가 지워지면 통신이 끊기는가?

실험 근거와 대조하기

반드시 그렇지는 않습니다. 이번에는 Flooding된 요청이 PC2에 도달하고 응답으로 FDB가 재학습돼 ping이 성공했습니다.

ARP에는 있고 FDB에는 없으면?

실험 근거와 대조하기

PC1은 새 ARP 없이 Unicast 프레임을 만듭니다. Switch는 위치를 몰라 Flooding합니다. ARP의 IP→MAC과 FDB의 MAC→Port는 별개입니다.

PC1과 PC2는 각각 언제 학습되는가?

실험 근거와 대조하기

PC1 ARP Request를 수신할 때 PC1→port 1, PC2 ARP Reply를 수신할 때 PC2→port 2가 학습됐습니다.
