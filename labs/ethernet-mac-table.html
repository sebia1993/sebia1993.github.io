02 · LEARN / FORWARD / RELEARN

무엇을 비웠는지가 결과를 바꿉니다.

ping 성공뿐 아니라 ARP·FDB의 전후 상태와
각 포트에 전달된 프레임을 함께 확인했습니다.

표 읽는 순서: 조건 만들기 → 명령 실행 → FDB·패킷으로 확인

ping은 모두 PC1에서 실행했습니다. PC2는 192.168.10.20, PC3는 192.168.10.30입니다. 모두 /24로 같은 서브넷에 있습니다.

01번은 PC2 응답을 잠시 막아 PC1만 학습되는 순간을 분리했습니다. 04번은 PC1 ARP를 유지한 채 SW1의 PC2 FDB만 지운 조건입니다. 모든 실험에서 ARP를 지운 것은 아닙니다.

번호조건 변경 / 확인 목적변경 후 수행한 테스트관찰 결과 / 판정근거
01Source MAC Learning
ARP·FDB 초기화 후 PC2 포트를 일시 down. PC1이 보내는 프레임만 관찰한 뒤 PC2 포트를 up.

PC2 응답을 막아 학습 시점을 분리

PC1 → PC2 ping, 이어서 FDB 확인
실제 테스트 명령
PC1> clear arp
SW1# ip link set eth1 down
PC1> ping 192.168.10.20 -c 1 -i 500 -w 1000
SW1# brctl showmacs br0
SW1# ip link set eth1 up
PC1> ping 192.168.10.20 -c 3 -i 500 -w 1000
PC1만 port 1에 학습. PC2 응답 후 PC2 MAC이 port 2에 추가.
✓ 실험·근거 검증 통과

03Broadcast
PC1의 ARP 캐시를 비우고 PC3를 찾도록 통신.

PC1이 PC3의 MAC을 모르는 상태

PC1 → PC3 ping + PC2 링크 관찰

04Unknown Unicast
SW1의 eth1만 분리·재등록해 해당 포트 FDB 삭제. PC1의 ARP는 남아 있음을 확인.

ARP는 유지하고 PC2 FDB만 제거

PC1 → PC2 ping 1회 + PC3 링크 관찰
실제 테스트 명령
PC1> show arp
SW1# brctl delif br0 eth1
SW1# brctl addif br0 eth1
SW1# brctl showmacs br0
PC1> show arp
PC1> ping 192.168.10.20 -c 1 -i 500 -w 1000
ARP 없이 PC2 MAC으로 보낸 Unicast 요청이 PC3에서도 동일한 바이트로 관찰.

05MAC 재학습

PC2 응답으로 위치를 다시 알게 된 상태

PC1 → PC2 ping 3회 재실행

06실제 Aging
기본 300초를 확인하고 5초로 변경. 동적 엔트리 확인 후 8초 추가 대기.

새 Bridge의 타이머만 5초로 조정

FDB 전후 비교 후 300초 복원
실제 테스트 명령
SW1# brctl setageing br0 5
SW1# brctl showmacs br0
# 8초 추가 대기
SW1# brctl showmacs br0
SW1# brctl setageing br0 300
PC1·PC2 동적 엔트리가 시간 경과로 사라짐. 수동 삭제와 별개로 실제 Aging 관찰.
✓ 실험·근거 검증 통과
터미널·FDB 보기 ↗

06번은 콘솔/FDB 기록으로 검증하며 PCAP은 별도 저장하지 않았습니다. 타이머를 5초로 조정한 실제 Aging이며, 기본 300초를 기다린 시험은 아닙니다. 실험 후 300초로 복원했습니다.

Broadcast의 목적지 MAC은 ff:ff:ff:ff:ff:ff입니다. 여기서 PC3에 보인 Unknown Unicast는 PC2의 실제 MAC을 목적지로 사용합니다. “Unknown”은 PC1이 아니라 Switch의 FDB 관점입니다.
04 · TWO TABLES, DIFFERENT ROLES

ARP가 남아 있어도 Switch는 모를 수 있습니다.

ARP · IP → MAC

누구에게 보낼 프레임인가?

PC1은 .20이 00:50:79:66:68:01임을 알고 있었습니다. 캐시가 남아 새 ARP 없이 바로 Unicast를 만들었습니다.

FDB · MAC → PORT

어느 포트로 내보낼 것인가?

SW1에서 PC2 포트의 학습 항목만 지웠습니다. 목적지 위치가 없어 요청이 PC2뿐 아니라 PC3 포트에도 전달됐습니다.

Source MAC Learning

응답이 돌아오면 다시 배웁니다.

PC2의 응답을 port 2에서 받고 PC2 MAC을 재학습했습니다. 다음 요청 3개는 PC3로 Flooding되지 않았습니다.

이번 FDB 삭제는 새 Bridge의 eth1을 잠깐 분리·재등록한 방식입니다. 실제 Aging 관찰은 06번에서 별도로 수행했습니다. 물리 스위치나 모든 VLAN 정책의 동작을 검증한 것은 아닙니다.

06 · EXPLAIN IN MY OWN WORDS

이제 결과를 자신의 말로 설명해 보세요.

본인 설명 확인 대기

먼저 답을 말해 본 뒤 근거를 펼쳐 비교하세요. 아래 내용은 Codex가 실험 증거로 작성한 참고 답안이며, 사용자 답변으로 기록하지 않았습니다.

Switch는 어느 MAC으로 학습하는가?

실험 근거와 대조하기

Source MAC입니다. PC2 응답을 막았을 때 FDB에 PC1만 생겼고, PC2의 ARP Reply를 받은 뒤 PC2가 추가됐습니다.

Destination MAC을 모르면 어디로 보내는가?

실험 근거와 대조하기

이번 동일 Bridge에서 수신 포트를 제외한 나머지 포트로 Flooding했습니다. PC2로 가는 요청이 PC3에서도 같은 바이트로 잡혔습니다.

Known Unicast는 어떻게 전달되는가?

실험 근거와 대조하기

FDB에 기록된 목적지 포트로 보냅니다. PC1→PC2 요청 3개가 PC2 링크에만 나가고 PC3에는 없었습니다.

Broadcast와 Unknown Unicast의 차이는?

실험 근거와 대조하기

둘 다 Flooding됐지만 Broadcast는 ff:ff:ff:ff:ff:ff, Unknown Unicast는 PC2의 실제 MAC 00:50:79:66:68:01을 목적지로 사용했습니다.

MAC Entry가 지워지면 통신이 끊기는가?

실험 근거와 대조하기

반드시 그렇지는 않습니다. 이번에는 Flooding된 요청이 PC2에 도달하고 응답으로 FDB가 재학습돼 ping이 성공했습니다.

ARP에는 있고 FDB에는 없으면?

실험 근거와 대조하기

PC1은 새 ARP 없이 Unicast 프레임을 만듭니다. Switch는 위치를 몰라 Flooding합니다. ARP의 IP→MAC과 FDB의 MAC→Port는 별개입니다.

PC1과 PC2는 각각 언제 학습되는가?

실험 근거와 대조하기

PC1 ARP Request를 수신할 때 PC1→port 1, PC2 ARP Reply를 수신할 때 PC2→port 2가 학습됐습니다.
