1단계 · CONCEPT GUIDE

DNS

목표는 하나입니다. IP는 정상인데 이름만 실패할 때 DNS Query가 어디까지 갔고 어떤 Response가 돌아왔는지로 문제 범위를 나눌 수 있으면 됩니다.

“Ping IP 성공”과 “DNS 정상”은 같은 뜻이 아닙니다.DNS Resolution과 실제 IP 통신은 서로 연결되지만 별도의 상태로 확인합니다.
1 · 개념서2 · Interactive Lab
이름을 물어보고 → Resolver가 Cache 또는 Upstream에서 답을 찾고 → 실제 통신은 그 IP로 진행합니다.

Query → Resolver → Cache/Upstream → Answer → IP Traffic

00 · 30초 핵심

DNS는 Query/Response와 실제 IP 통신을 나눠서 봅니다.

① Query: Client가 QNAME + QTYPE을 DNS Server에 물어봅니다.

② Resolver: Cache에 답이 없으면 Recursive/Caching Resolver가 configured Upstream DNS에 다시 Query합니다.

③ Cache: TTL이 남아 있으면 같은 이름은 Upstream까지 가지 않고 Cache에서 바로 답할 수 있습니다.

④ 장애: Response가 없는 상태와 NXDOMAIN(RCODE=3)처럼 Error Response가 돌아온 상태는 다릅니다.

01 · QUERY / RESPONSE

이름 하나를 A Record로 해석하는 기본 흐름입니다.

1

Client Query

app.lab.test의 A Record를 198.51.100.2 Resolver에 요청합니다.

2

DNS Answer

같은 Client-side DNS ID로 A=203.0.113.10이 돌아왔습니다.

3

TTL

이번 Authoritative Answer의 TTL은 10초였습니다. 이 숫자를 보편값으로 일반화하지 않습니다.

4

실제 통신

Name Resolution 뒤 203.0.113.10으로 ICMP Echo 3/3이 정상 전달됐습니다.

02 · RECURSIVE / UPSTREAM

Cache Miss이면 R2가 R3에 다시 물어봅니다.

CLIENT → R2

RD=1 · DNS ID 21456

PC1은 R2에 Recursion Desired Query를 보냈습니다. 이 Client-side Query와 최종 Client Response는 같은 DNS ID로 대응됐습니다.

R2 → R3

Upstream DNS ID 31909

R2는 R3에 별도의 Upstream Query를 만들었습니다. Resolver가 DNS ID를 다시 쓸 수 있으므로 두 Leg를 ID 동일성만으로 연결하면 안 됩니다.

이번 Lab의 범위: R2가 configured Upstream Authoritative DNS인 R3에 Query하는 구조를 검증했습니다. Root/TLD 전체 Iterative Resolution을 재현했다고 표현하지 않습니다.
03 · CACHE

첫 Query와 두 번째 Query의 Upstream 경로가 달라졌습니다.

CACHE MISS · PC1

R2 → R3 Query 발생

Cache를 비운 뒤 PC1이 app.lab.test를 조회하자 R2가 R3까지 Query했고 TTL 10의 A Record를 받았습니다.

PC1 → R2 → R3 → R2 → PC1
CACHE HIT · PC2

새 Upstream Query = 0

약 3.6초 뒤 PC2가 같은 이름을 조회했을 때 R2가 TTL 6의 Cached Answer를 반환했고 R3로 새 Query는 없었습니다.

PC2 → R2 → PC2 · R3 Query 없음
관찰 포인트: Cache Miss 전달 응답은 이번 IOS에서 AA=1, Cache Hit 응답은 AA=0이었습니다. 이 표기는 이번 구현 Actual로만 사용합니다.
04 · 장애를 Response/Stop 위치로 구분

“이름이 안 된다”는 증상도 원인은 서로 다릅니다.

DNS SERVICE DOWN

Query는 R2까지 도착

R2의 DNS Service를 내리자 IP Ping은 3/3 유지됐고 Query는 R2까지 도착했지만 DNS Response는 없었습니다. 이번 IOS는 ICMP Type3 Code3도 반환했습니다.

IP ✓ · Query → R2 ✓ · DNS Response ✕ · Client Cannot resolve
WRONG CLIENT DNS

실제 Resolver까지도 못 감

PC1 DNS를 존재하지 않는 192.0.2.254로 바꾸자 .254 ARP만 발생했고 Reply는 0, 실제 R2 Query도 0이었습니다. IP Ping은 계속 정상입니다.

IP ✓ · ARP .254 ✕ · Query → R2 ✕
NXDOMAIN

Response는 존재함

recover.lab.test Record를 제거하자 R3가 RCODE=3 Response를 실제로 반환했고 Client도 NXDOMAIN을 받았습니다. 이는 Timeout이 아닙니다.

Query ✓ · DNS Response ✓ · RCODE 3 · A Answer ✕
05 · REVIEW

여기까지만 기억하면 1단계 완료입니다.

⭐ 꼭 기억하세요

  • DNS Query와 실제 IP Traffic은 별도 단계로 확인합니다.
  • Cache Miss는 Upstream Query가 필요하지만 TTL-valid Cache Hit는 생략할 수 있습니다.
  • Recursive Resolver가 Upstream에 Query할 때 DNS ID가 달라질 수 있습니다.
  • DNS Server Down과 Wrong Client DNS는 Query가 마지막으로 보이는 위치가 다릅니다.
  • NXDOMAIN은 Response이고, 무응답/Timeout과 다릅니다.
내 말로 설명하기

“IP는 되는데 이름만 안 될 때 무엇부터 볼까?”

Client DNS 주소, Query 위치, Response 유무, RCODE라는 네 단어를 사용해 설명할 수 있다면 충분합니다.
