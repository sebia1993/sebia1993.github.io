AP 전환 사실과 전환 이후 서비스 상태를 분리해 설명합니다.

앞선 학습 · 802.1X / EAP / RADIUS까지의 개념을 연결합니다.

01 · 질문과 그림으로 시작

다른 AP로 옮겨 붙었는데 인터넷이 안 되면 모두 로밍 실패일까요?

30초 핵심 · 로밍은 단말이 접속한 AP의 무선 영역을 바꾸는 일입니다. AP가 바뀌었는지 먼저 보고, 이후 인증·주소·정책·경로가 정상인지 별도로 확인합니다.

02 · 방금 본 그림에 이름 붙이기

이름보다 역할을 먼저 기억하세요.

802.11k / 802.11v
k는 후보 AP 정보를 얻는 데, v는 전환 제안을 주는 데 도움을 줍니다. 제안이 실제 전환 완료와 같지는 않습니다.
802.11r / FT
보안 전환 부담을 줄여 빠른 전환을 돕는 방식입니다. FT는 Fast Transition입니다.
Sticky Client
더 나은 후보가 있는데도 관찰 구간 동안 기존 AP에 머무는 단말을 말합니다. 약한 신호 하나만으로 확정하지 않습니다.

03 · 동작 순서

핵심 흐름을 연결해 봅니다.

  1. 같은 단말의 전후 BSSID·AP가 실제로 달라졌는지 확인합니다.
  2. 연결·보안 전환 결과를 확인합니다.
  3. 주소, 적용 정책, 전달 경로를 나눠 확인합니다.
  4. 단서가 맞지 않으면 이전 단계로 돌아갑니다. 이는 진단 순서이지 엄격한 프로토콜 실행 순서는 아닙니다.

04 · 헷갈리는 지점

헷갈리는 의미를 구분해서 읽으세요.

구분뜻
AP 전환 성공접속 대상이 바뀌었다는 근거입니다.
전환 뒤 서비스 성공실제 데이터가 다시 왕복한다는 별도 근거가 필요합니다.

05 · 복습

꼭 기억할 세 가지

  • 전환 사실과 이후 통신은 따로 확인합니다.
  • k·v·r은 서로 다른 역할입니다.
  • 모든 끊김을 RF·로밍 문제로 단정하지 않습니다.

1단계 · CONCEPT GUIDE

Roaming / WLAN Troubleshooting

“로밍했는가?”와 “로밍 후 서비스가 되는가?”를 분리하는 것이 이번 학습의 핵심입니다. 모든 끊김을 RF나 Roaming 문제로 몰아가지 않습니다.

Roam Gate → Service Gate

RF → Association → Authentication → Addressing → Policy / Authorization → Routing

00 · 30초 핵심

Roaming은 “Client가 다른 BSS로 이동한 사실”부터 확인합니다.

ROAM

실제 전환의 핵심은 BSSID/AP 변화

공식 Cisco trace에서는 같은 STA가 old BSSID에서 target BSSID로 이동하고 FT 재연결이 기록됩니다. 다만 이는 공개 Reference이며 사용자 단말의 실측은 아닙니다.

ASSISTANCE

Infrastructure는 도울 수 있지만 결정과 결과는 구분

11k Neighbor 정보, 11v Transition 제안, ClientMatch Steering은 후보 선택을 돕습니다. 제안을 받았다는 사실만으로 실제 Roam 성공을 뜻하지 않습니다.

AP-A
Source BSS
AP-B
Target BSS
STA-A
Reference View: AP-A → AP-B BSSID 전환과 FT 성공은 공식 사례에서 확인. 사용자 단말의 RF 임계값·이동시간·실제 중단시간은 미측정.
01 · 802.11k / v / r

세 기능은 같은 일을 하지 않습니다.

k

Candidate Information

Neighbor / Radio Resource 정보를 제공해 Client가 후보 AP를 찾는 데 도움을 줍니다.

“어디를 볼까?”
v

Transition Assistance

BSS Transition 제안이나 Vendor Steering으로 더 나은 후보를 권할 수 있습니다.

“이쪽으로 가보는 건 어때?” · 강제 성공 보장 아님
r

Fast Transition

BSS 전환 시 보안 전환의 부담을 줄여 빠른 Roam을 돕습니다.

“보안 전환을 더 빠르게”
ROAM-03 LIMIT

FT 성공과 Data Resume는 같은 증거가 아닙니다.

검토한 Cisco trace에는 FT 성공이 있지만, 제공된 RUN 시각이 해당 재연결보다 앞서 있어 그 항목으로 전환 후 데이터 재개를 증명할 수 없습니다. 따라서 “무손실”, “중단시간 X ms”, “Ping 성공”을 만들어 넣지 않습니다.

02 · STICKY CLIENT

약한 RSSI만으로 Sticky Client라고 부르지 않습니다.

Sticky 판정에 필요한 두 조건

현재 AP-A상대적으로 나쁜 RF
vs
후보 AP-B실제로 더 좋은 RF

그리고 일정 관찰 구간 동안 Client가 계속 AP-A에 남아 있어야 합니다.

이번 검증의 한계

Aruba ClientMatch의 공식 설명으로 Sticky 조건을 정리했지만, 이번에는 AP 2대의 실제 시계열 RF와 체류 구간을 측정하지 않았습니다.

금지된 결론: 약한 RSSI 하나, 주변 BSSID 수, 또는 Steering 이벤트 하나만으로 Sticky를 실측했다고 표시하지 않습니다.

05 · REVIEW

이 다섯 문장을 설명할 수 있으면 1단계 완료입니다.

⭐ 꼭 기억하세요

  • 실제 Roam 증거는 BSSID/AP 전환입니다.
  • 11k는 후보 정보, 11v는 전환 제안, 11r은 Fast Transition입니다.
  • FT 성공만으로 전환 후 Data Resume가 자동 증명되지는 않습니다.
  • Sticky는 약한 RSSI가 아니라 “더 좋은 후보 + 현재 AP에 계속 머묾”이 필요합니다.
  • Roam 이후 장애는 DHCP·Policy·Routing으로 내려가 분리합니다.
